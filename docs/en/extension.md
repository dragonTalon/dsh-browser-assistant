# Chrome extension (packages/extension)

An MV3 extension in three parts: **service worker (control center) + content script (the only part that touches the DOM) + side panel (chat UI)**. It never talks to dsh sessions directly — everything goes through the background.

## The three parts

| Part | Responsibility | Key files |
|---|---|---|
| **background/** | bridge client (discovery/reconnect/heartbeat), RPC forwarding and frame codec, tool dispatch, approval coordination, current-page tracking, logging | `index.ts` (assembly), `bridge.ts`, `frames.ts`, `types.ts`, `rpc.ts`, `tools.ts`, `authorization.ts`, `approval-coordinator.ts`, `navigation.ts`, `region.ts` |
| **content/** | page → text snapshot, perform click/type/scroll/navigate, stable numbering, sensitive masking, region selection | `index.ts`, `snapshot.ts`, `extract.ts`, `actions.ts`, `ids.ts`, `privacy.ts`, `region.ts` |
| **panel/** | chat, session picker, slash commands & skills, model selection, region capture, Markdown rendering, logs, approval box, Q&A box, system config | `main.ts` (composition root) + `transport`/`conversation`/`session-selector`/`slash-command`/`slash-command-text`/`model-selector`/`region`/`question`/`approval`/`status`/`settings`/`errors`/`log` + shared `common/` (`tools/` + `ui/` + `slash-catalog` + `session-list` + `session-events` + `connection-state` + `region`); `index.html` |

## Core mechanisms

### Connection & liveness
- **Discovery**: with an empty `host`, probe ports → `fetch /ext/bridge-config` → `WebSocket` → `hello` handshake. Frame shapes and the handshake exchange are in [protocol.md](protocol.md).
- **Remote dsh**: the gear button in the status bar opens the **System config** dialog for `dsh host` + `token`. Four address forms are accepted — `10.0.0.7:3080`, `localhost:3080`, `wss://dsh.example.com`, and a full `ws://host:port/ext/bridge`: a missing scheme gets `ws://` plus `/ext/bridge`, an explicit scheme is kept (`http`/`https` map to `ws`/`wss`), and a sub-path is preserved for reverse proxies mounted off the root. A non-empty `host` **never falls back to local discovery** — a wrong remote address must read as unreachable, not quietly connect to this machine.
- **Verify at config time**: typing shows the effective address live (computed locally, no request); `Test connection` runs a full `hello` handshake on a **separate one-shot socket** (it never evicts the working connection) and reports the failure stage separately: malformed address / unreachable / reachable but token rejected (`4002`) / reachable but handshake timed out; `Save & reconnect` waits for the real reconnect and, on failure, keeps the dialog open with the input intact.
- **Token**: mandatory for remote connections (the server enforces it for every non-loopback source, no exceptions). Read it on the dsh machine with `cat ~/.dsh/ext-bridge-token`; pasted **surrounding whitespace is stripped automatically** — the token file ends with a newline and the server compares bytes exactly, so keeping it would reliably produce `4002`.
- **Reconnect**: exponential backoff (500ms→10s cap + jitter); `4000` means "superseded" and stops directly without mutual kicking.
- **Anti SW suspension**: panel 20s heartbeat + 30s alarm, double insurance against idle suspension killing the WebSocket; on disconnect clears "working", on reconnect pulls `session.history` to recover missed final output.

### Tool dispatch & approval
- Receives `tool.call` → resolves the controlled tab → builds an approval prompt (`authorization.ts` pure function) → routes through `approval-coordinator` (60s window) if approval is needed → dispatches to the content script → `tool.result`.
- **Reads default to auto** (`browser_snapshot`/`get_text`); **page-changing actions follow the session permission tier** — refused under `read-only`, fail-closed approval under `workspace-write`, direct execution under `danger-full-access`; no panel → timeout reject.
- **Tool semantics come from the shared registry**: names and classifications (read/observe/mutate/navigate, delta attachment, navigation candidacy) are declared by the protocol package's `browser-tools.ts`; the approval judgement in `authorization.ts` and the delta/navigation policies in `tools.ts` derive from it, and no local classification table exists in the extension (drift guard: see the tool-registry section of [bridge-plugin.md](bridge-plugin.md)). `background/types.ts` gathers `ToolCall`/`ToolAnswer`/`ContentBudget`/`TabFrame`, and `BridgeState`/`RegionElement`/`RegionRect` live in `common/` — the panel takes no types from background runtime modules and the background takes none from content modules.
- Validates "target still valid" before dispatch (document id match), avoiding wrong actions if the page changed during approval.

### Page snapshot (text-first)
- **Stable numbering**: `WeakMap<Element,number>` one-time assignment + `data-dsh-el`, stable across snapshots.
- **Naming**: aria-label → label → aria-labelledby → visible text → placeholder (the ARIA priority chain in `extract.ts`).
- **Body extraction**: "readability-lite" — `<main>` → single `<article>` → largest text block with ≥2 paragraphs, scored.
- **Delta snapshots**: return only changes/removals/renumbering to save tokens.
- **iframes**: discovered via `webNavigation.getAllFrames`; the main frame gets an 80% budget, subframes split the rest; addressed as `(frame,index)`.
- **Settle detection**: `MutationObserver` + `readystatechange`, layered by action type (click/type/scroll each have their own strategy); stable pages return in seconds, continuous animation has a hard cap.

### Privacy
- Passwords/card numbers/CVV are detected by `type=password`, `autocomplete=cc-*`, id/name/aria-label regexes, masked as `••••`, and never sent back.
- Page text is wrapped in a random-nonce "untrusted content" boundary to prevent prompt injection (defense in depth; approval is the enforcing boundary).

### Current-page awareness
- `tabs.onActivated`/`onUpdated`/`windows.onFocusChanged` track the active tab (URL + title), shown live in the panel, and injected on `session.prompt` as `[网页描述]：<title> (<url>)` to give the model context.

### Chat & interaction
- **Simple chat**: the session identity comes from the session picker; the first send is what runs `session.create` → `session.prompt` → subscribe to the `event` stream and render; the "working" indicator covers the whole "think → call tools → execute → output" flow (strictly follows the turn: `turn/start` shows, `turn/end` clears, intermediate text/tool events do not clear).
- **Session picker**: the status bar's "session" dropdown, whose first entry is always "new session" and is selected by default. Candidates come from the read-only `session.list`: blank sessions and sub-agent sessions are excluded, the rest are ordered by most recent activity and capped at 50 (a disabled note marks the cut-off), each starting with a `[working-directory name]` bracket prefix (omitted when the directory is unknown) followed by the title (falling back to the first 8 characters of the session id), a running marker and the relative activity time. **Opening or reconnecting never creates a session** — creation happens on the first send, on the first model pick for this session, or when the slash-command menu is opened from the "new session" state (the command catalog is resolved per session, so the menu needs one; see the slash-command bullet). Merely opening the panel still leaves no orphan session, but typing `/` once in "new session" does create one. Picking a past session binds it and replays `session.history` (clear, then replay in order; `hasMore` shows an "older messages not shown" notice at the top). It deliberately does **not** go through `session.create { sessionId }`: that path injects the bridge's configured `sessionWorkspace`, so a session living elsewhere fails with `session/conflict` and would be re-homed into that workspace; a cold session is resumed by dsh itself on the next prompt. Events are isolated per `sessionId` (leftover frames of the previous session are dropped at the switch), live frames arriving during a replay are buffered by `seq` and applied after it, switching never cancels the previous session's running turn, and switching back relies on the bridge's per-session cursor backfill. dsh questions and browser-action approvals are **deliberately not session-filtered**: while a session the user switched away from still has a pending interaction, the panel is its only answerer.
- **Model selection & capability marking**: the pill-shaped dropdown on the right of the composer (right-aligned, same feel as the dsh GUI) re-pulls `model.catalog` (read-only) after every connect. Current selection resolves in order: session-history `projections.values.modelSelection` `next` → `lastUsed` → catalog `default`; three sync channels — optimistic update on `session.selectModel` success, instant alignment on `model/selection` events, and projection fallback on reconnect `session.history`. Multimodal marking is ternary: `inputModalities` containing `image` → "vision", published without it → "text", unpublished or absent from the catalog → "capability unknown" (never guessed); the current model's capability also shows as a small badge beside the dropdown. Choosing in the dropdown calls `session.selectModel`; **that dsh behavior also rewrites the deployment default model** (`agentDefaultModel.saveSelection`) — the panel says so persistently in the selector tooltip. A catalog fetch failure shows "model unavailable" on the selector plus an error-coded line in the conversation, and never blocks chat.
- **Permission tier & page sharing (two orthogonal axes)**: the pill-shaped dropdown on the left of the composer (right after the region-capture button) is the **session permission tier** (capability axis), labelled exactly as the dsh interface labels it (`read-only` / `workspace-write` / `danger-full-access`). Both the current value and the candidates come from session history `projections.values.permissions` (`currentValue` / `options`) — **candidates are never hardcoded**, a deployment's own preset names show as published, and a tier the bridge does not recognize is shown truthfully as "custom" and is not selectable. Switching goes through a bridge RPC (`permission.set` → dsh's `/permission <preset>`); **the projection flowing back is the only evidence a switch took effect**, never the write's return value, so "the write succeeded but the tier did not change" can never display as success. Selecting `danger-full-access` always passes a risk gate first (checkbox-style, **asked again every time, never remembered**) whose copy states both that browser actions stop needing confirmation and that the tier also opens the session's dsh-side file and command permissions.
  **The tier is configurable before any session exists.** In the "new session" state there is no bound session, but the deployment's tier table is read from any session's projection via `session.list` (read-only; it creates nothing), so the control still lists candidates and accepts a pick. Picking one is what creates the session, the same lazy creation the first model pick already triggers — merely opening the panel still leaves no orphan session. The **page sharing** control in the system-config dialog is the privacy axis (`auto` / `ask` / `off`): it decides only whether page content may be read and sent to the model, and it is independent of the tier. It applies on the change event rather than on "save & reconnect", because the preference takes effect on the next tool call. This control is what makes the preference written by the approval dialog's "always allow reads" **visible and revocable** — previously no panel surface could read it.
  The tier has three sync channels: the session-history projection is the baseline, the `session/permission` event the bridge pushes on an **actual** change is the increment, and the optimistic update on a panel switch is immediate feedback — the projection wins on conflict. Changes while disconnected are not pushed; the panel catches up from the projection baseline the next time it opens the session or reloads history, which is sufficient because a tier is a current-value snapshot with no intermediate states to backfill.
- **dsh questions** (`ask_user_question`): `question/requested` pops a question box (options / custom input), answers return via `respond`.
- **Slash commands & skills**: a `/`-prefixed draft opens an overlay above the composer listing the **currently bound session**'s two slash vocabularies — **host commands** (`commands.list`: name + host description + host-published argument hint) and **user-invocable skills** (`skills.list`: name + description, with user-only skills marked). Filtered by containment over the text after `/`; ↑/↓ move across rows, Enter picks, Esc closes (keeping the draft), clicking a row picks, clicking outside dismisses. Picking only writes `/<name> ` back into the composer — it neither executes nor sends. **A name published by both namespaces resolves to the command**, matching the host's own adjudication. The catalog refreshes on session bind, on connect, after every successful send, and on the menu's first use. Both namespaces are per-session, so a `/` typed in the "new session" state **creates and binds a session on the spot** and then reads the catalog for it — the panel never resolves against an existing session the user did not pick. Note that the *command* catalog resolves through an `agentId` lookup that resumes an inactive session (the skill catalog does not — it observes the session through `sessionQuery`), so **opening the menu activates the bound historical session**. The menu is never silent when it has nothing to offer: "starting a session…", "loading commands…", "command list unavailable — reconnect to retry" and "no matching command" each get their own non-selectable explanatory row.
  - **The two vocabularies are invoked differently**: a **command** goes through `commands.execute` (whole line, verbatim) and **opens no turn, produces no user message, and never raises the "working" indicator** (that indicator strictly follows the turn lifecycle, and a command has no turn); a **skill has no execute endpoint at all** — the panel sends `/name` as an **ordinary message**, and the host's pre-step gesture recognition injects the skill body (`source.kind === 'user'` prompt text is exactly the payload it expects), so a skill produces a normal turn and reply.
  - **Availability & arguments**: every catalog entry is selectable and executable, and the panel makes no local capability judgement — the host is the sole authority on each command's own grammar. A command line **may carry arguments**, and the panel hands the whole line to the host unchanged (`/goal clear`, `/permission workspace-write`, `/plan off` and `/feedback <text>` are all the documented forms). An earlier revision kept an allowlist of "useful without arguments" commands and marked the rest "not supported yet"; that was wrong — the panel is a plain textarea, and 4 of this deployment's 6 host commands are normally used *with* arguments, so blocking them gutted the feature. Menu rows show the argument hint alongside the description.
  - **Input methods and catalog lifetime**: an Enter pressed while an IME is composing is **never consumed by the menu** — that key accepts the candidate, it does not pick a row (both `isComposing` and `keyCode === 229` are checked, because the committing Enter can arrive after `compositionend`). The catalog is **cleared when the connection drops**: its entries name a host the panel can no longer reach, so opening the menu before reconnecting reports "command list unavailable" instead of showing the previous host's commands.
  - **Command timeouts are reported honestly**: a command execution request (`commands.execute`) can outlive the client's wait budget (e.g. `/compact` summarizing a large conversation). On timeout the panel says only that the command **did not answer within the limit, may still be running, and that the event stream owns the outcome** — it never claims the command failed or was cancelled, since the authoritative outcome is the `command/run`/`command/done` pair. The bridge additionally applies its own, wider bound (120s, far above the client's 30s) to session-ordered calls; exceeding it releases that session's queue slot so a long command cannot block later messages indefinitely. The bridge does **not** guarantee that the host's command handler is aborted — whether a command honours cancellation is up to that command.
  - **A failed skill catalog never costs the commands**: an unreadable skill catalog (or a deployment mounting no skill registry, or a session with no cwd) degrades to "no skills this time", while the commands stay usable; only a failed **command** catalog shows "command list unavailable".
  - **Submit routing**: a resolved entry is routed by its namespace (command → `commands.execute`; skill → ordinary prompt); a failed catalog read reports why and is **not sent**, keeping the draft; a `/`-prefixed draft naming nothing in either namespace (e.g. `/etc/hosts`) is sent as an ordinary message, matching the dsh Web GUI's unmatched behaviour. A pending region capture keeps priority — the menu never swallows that intent.
  - **Lifecycle rendering**: a command row is driven **only** by the durable `command/run` (creates the "running…" row) and `command/done` (settles the row by `commandId` into ✓/✕ plus the result text) events, never by the RPC acknowledgment. Live view and history replay therefore share one rendering path and agree by construction; a result event arriving before its start event (truncated history) creates the row in place rather than being dropped. An RPC timeout is diagnostics only, never a failure verdict (the event stream owns the outcome), while any other admission rejection — which no lifecycle event will explain — is reported. Command names, arguments, host descriptions and result text are always rendered as plain text and never reach `innerHTML`.
- **Status/logs**: a top status bar (connection state + address + reconnect count + current page) + a collapsible log panel (info/warn/error color-coded, ring-buffer replay).

## Security model

| Boundary | Mechanism |
|---|---|
| Bridge auth | bearer token (5s hello, constant-time); mandatory for remote connections |
| Loopback passwordless | only `chrome-extension://` Origin |
| Privileged methods | non-loopback rejects `settings.*`/`credentials.*`/`host.openPath`/`host.pickDirectory` — **these features are unavailable on a remote connection**; the panel states it as "local dsh only" instead of echoing a raw error code |
| Connection target | `connect-src` allows any `ws://`/`wss://` (needed for remote deployments); only the target widened — token auth, the tier gate, approvals, and the loopback fence are unchanged |
| Page data | text-only, no screenshots; sensitive fields masked; untrusted-content wrapping |
| Actions (capability axis) | graded by the **session permission tier**: `read-only` refuses page changes and page opening outright (the `tool.call` never leaves the process); `workspace-write` is fail-closed approval (no answer = refuse, 60s timeout = refuse); `danger-full-access` executes directly and raises no approval request |
| Tier source | the bridge solves it from the dsh session's `permissions` projection and sends it with each `tool.call`; the extension **takes no part in solving it**, never derives it from local config, and no claim it makes counts as authorization |
| Page sharing (privacy axis) | a local preference **orthogonal** to the tier: `auto` allows page reads, `ask` confirms each one, `off` refuses them all. Read strength follows this alone at any tier — a tier widens what the agent may DO, never what data may leave the page |
| Immovable core | tier resolution cannot be influenced by the extension, so the source of authorization cannot be forged. This is the invariant that survives replacing "writes always need approval" with tiers |

### TLS reverse proxy (recommended for remote)

Plain `ws://` across a network sends page snapshots, prompts, and the token in the clear. Terminate TLS in front of dsh and connect with `wss://`:

```nginx
# dsh web listens on 127.0.0.1:3080; the proxy exposes only wss
server {
  listen 443 ssl;
  server_name dsh.example.com;
  ssl_certificate     /etc/letsencrypt/live/dsh.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/dsh.example.com/privkey.pem;

  location /ext/ {
    proxy_pass http://127.0.0.1:3080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;      # /ext/bridge is a WebSocket upgrade
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;                    # the bridge keeps alive via ping; don't idle-timeout it
  }
}
```

Enter `wss://dsh.example.com` in the dialog (the extension appends `/ext/bridge`); for a sub-path mount enter the full path (e.g. `wss://dsh.example.com/dsh/ext/bridge`). The token is still `~/.dsh/ext-bridge-token` **on the remote machine**.
